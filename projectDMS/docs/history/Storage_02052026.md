# Storage Audit - 02 May 2026

## Current State

This codebase is primarily a FastAPI + React document management system backed by MongoDB, local filesystem storage, optional S3-compatible object storage, Qdrant, FalkorDB/RedisGraph, and Redis. There is no active PostgreSQL implementation in the runtime paths inspected. A root dependency file mentions `sqlalchemy-orm`, but the backend runtime connects to MongoDB through Motor/PyMongo and no PostgreSQL service is defined in `docker-compose.yml`.

Active runtime entrypoint:

- `backend/rbac_backend/main.py` mounts `documents`, `contracts`, `storage_sync`, `storage_settings`, `retrieval_engine`, and other API routers.
- `backend/rbac_backend/core/database.py` creates a Motor client from `settings.DATABASE_URL` and then explicitly uses the MongoDB database named `contraclaim`.
- `docker-compose.yml` defines `mongo`, `qdrant`, `falkordb`, and `redis` volumes.
- `backend/rbac_backend/routers/folder_structure.py` and `backend/rbac_backend/documents.py` contain additional file/S3 logic, but they are not mounted by `main.py`; they should be treated as inactive or legacy unless another deployment imports them.

Primary stores:

| Store | Current role | Persistence |
| --- | --- | --- |
| MongoDB `contraclaim` | Source of truth for document metadata, contract upload state, vector records, comments, notifications, jobs, folders, letters, audit-style app state | `mongo_data` Docker volume |
| Local filesystem | Original uploaded binaries, chunk temp files, contract processing copies, OCR/processed outputs, generated summary text files | `SECURE_UPLOADS_DIR`, `UPLOADS_DIR`, temp dirs |
| S3-compatible object storage | Optional secondary/primary binary copy through `StorageSettingsService` provider selection | External bucket; currently config naming mismatch exists |
| Qdrant | Vector search index for retrieval and contract clause search | `qdrant_data`, `qdrant_snapshots` volumes |
| FalkorDB/RedisGraph | Graph representation of letter references and contract clause graph | `falkordb_data` volume |
| Redis | Contract ingestion durable queue; LangGraph service state; not used as app cache in main backend | `redis_data` volume |
| In-memory cache | AI assistant and performance endpoint cache | Process memory only |

## Mapping

### General Document Model

General documents are stored in MongoDB collection `documents` using `backend/rbac_backend/models/document.py`.

Important fields:

- Identity and scope: `_id`, `organization_id`, `project_id`, `createdBy`
- Binary pointers: `filename`, `filepath_local`, `filepath_s3`, `presigned_url`, `storage_locations`
- File metadata: `filetype`, `filesize`
- Business metadata: `uploadType` (`incoming`, `outgoing`, `contract`), `letterNo`, `letterNoNormalized`, `date`, `subject`, `from`, `to`, `tags`, `subTags`, `status`
- Processing output: `ocrText`, `full_text`, `summary`, `keywords`, `contractual_clauses`, `reference`, `processing_metadata`, `processed_path`, `processing_error`
- Contract overlay fields: `contract_upload_id`, `contract_categories`, `contract_error`
- Relationship fields: `enclosures`, `references`, `referencedBy`
- Nominal version field: `version`, default `"1.0"`

The `version` field is not used as a document versioning mechanism. Updates overwrite the same MongoDB document.

### General Document Save Flow

Endpoint: `POST /api/documents`

Active path:

1. `backend/rbac_backend/routers/documents.py` receives a single `UploadFile` plus metadata.
2. `DocumentController.create_document` checks project permission and document access.
3. Uploaded bytes are read fully into memory.
4. MIME validation uses `validate_file` and `settings.ALLOWED_DOCUMENT_MIMES`.
5. `StorageSettingsService.resolve_settings` loads org/project storage provider settings from MongoDB collection `storage_settings`.
6. `_write_to_providers` writes to enabled providers:
   - `local`: `SecureFileService.store_document` writes under `SECURE_UPLOADS_DIR` using resolved base path segments.
   - `s3`: `S3Service.upload_bytes` writes to object storage and stores the object key.
   - `azure`, `gcs`, `custom`: currently marked as skipped; no actual implementation.
7. `DocumentService.create_document` inserts the `documents` record.
8. If OCR is enabled, `DocumentService.queue_document_processing` schedules an in-process background job.
9. A `NEW_UPLOAD` notification is emitted into MongoDB `notifications`.

Storage settings path templates currently resolve only to broad folders:

- Incoming default: `/ORG/PROJ/incoming`
- Outgoing default: `/ORG/PROJ/outgoing`
- Contracts default: `/ORG/PROJ/contracts`

Actual local path is rooted at `settings.SECURE_UPLOADS_DIR`; path template segments are sanitized and appended below that root.

Target canonical policy should be stricter and deterministic:

- Incoming documents: `/ORG/PROJ/incoming/{yyyy}/{mm}/{upload_id}_{safe_letter_no}{ext}`
- Outgoing documents: `/ORG/PROJ/outgoing/{yyyy}/{mm}/{upload_id}_{safe_letter_no}{ext}`
- Contract documents: `/ORG/PROJ/contracts/{upload_id}_{safe_filename}`

For correspondence documents, `safe_letter_no` should be derived from the document `letterNo`, not from the uploaded filename. This makes the filesystem/object key searchable and consistent with DMS metadata. The original uploaded filename should still be stored separately as `original_filename` or `filename` for traceability. This keeps all documents for one organization and project under one project folder, while separating correspondence direction and contract masters. The same relative key must be used for local storage and object storage; only the provider root differs.

### General Document Processing Flow

Background path:

1. `DocumentService.process_document_async` reloads the document from MongoDB.
2. If local file is missing and `filepath_s3` exists, it downloads bytes from S3 into a temp directory.
3. `DocumentProcessor.process_document` validates size, runs OCR, uploads the processed file to OpenAI, extracts metadata/content, and deletes the OpenAI file afterward.
4. `FileService.save_summary` appends extracted content to a Markdown summary under `uploads/<org>/<project>/incoming.md`, `outgoing.md`, or `projectid.md`.
5. `DatabaseService.save_document_data` updates the `documents` record with OCR text and parsed metadata.
6. `DatabaseService._create_and_store_embeddings` chunks text and writes vectors:
   - MongoDB `document_vectors`: full text chunk records plus embedding arrays.
   - Qdrant: dual-write through `LangChainVectorService.replace_document` when configured.
   - MongoDB `vector_sync_status`: sync status, Mongo chunk count, Qdrant chunk count.
7. `GraphIngestionService` attempts to sync document metadata and references into FalkorDB.
8. `ReferenceSyncService` updates bidirectional document references when metadata references resolve.

### General Document Retrieval Flow

Metadata retrieval:

- `GET /api/documents` builds an authorized Mongo query via `AuthorizationService.build_document_query`.
- It reads `documents`, enriches project/tag display metadata, and returns `DocumentListResponse`.

Single document:

- `GET /api/documents/{id}` loads a `documents` record after RBAC checks.

Binary download:

- `GET /api/documents/{id}/download`
- Prefers `filepath_local` when the file exists.
- Falls back to S3 presigned URL from `filepath_s3`.
- Falls back to stored `presigned_url` if present.

Vector search:

- `GET /api/documents/vector-search` uses `LangChainVectorService.similarity_search` over Qdrant and then fetches matching `documents`.

Retrieval engine:

- `POST /api/v1/ingestion/jobs` creates an `ingestion_jobs` record and processes `documents.full_text` or `ocrText`.
- It writes normalized chunks to MongoDB `chunks`, upserts Qdrant vectors through `VectorClient`, prunes stale vectors, and updates `vector_sync_status`.
- `POST /api/v1/retrieval/search` and `/rag` search Qdrant by default when healthy, or MongoDB `chunks` when configured/requested.

### General Document Update Flow

Endpoint: `PUT /api/documents/{id}`

1. Controller loads the existing document and checks access.
2. `DocumentUpdate` allows metadata fields only: `uploadType`, `letterNo`, `date`, `subject`, `from`, `to`, `tags`, `subTags`, `status`, and path structure fields.
3. The controller merges the update into the existing `Document` model.
4. `DocumentService.update_document` overwrites the MongoDB record with `$set` of the model dump.
5. No document version is created.
6. No binary replacement path exists in this endpoint.
7. No audit record or immutable event is written for document metadata changes.

### General Document Delete Flow

Endpoint: `DELETE /api/documents/{id}`

1. Controller loads document and checks delete access.
2. `DocumentService.delete_document` performs `db.documents.delete_one({"_id": doc_oid})`.
3. It does not delete:
   - Local binary file
   - S3 object
   - `document_vectors`
   - Qdrant points
   - `chunks`
   - FalkorDB graph nodes/edges
   - `document_comments`
   - `notifications`
   - `vector_sync_status`
   - Reverse `referencedBy` entries on other documents
4. There is no trash/archive stage and no retention workflow.

### Enclosure Handling

Endpoint: `POST /api/documents/{id}/enclosures`

Current active implementation validates enclosure bytes but does not store the enclosure binary. `DocumentService.add_enclosure` only pushes metadata into the parent `documents.enclosures` array with `filepath_local=""` and `filepath_s3=None`.

Impact: the API can list enclosure metadata, but the active path does not persist downloadable enclosure files.

### Bulk Upload Handling

Endpoint: `POST /api/documents/bulk-upload`

1. CSV is parsed with `BulkUploadService.read_csv_from_upload_file`.
2. Uploaded files are persisted to temp files via `BulkUploadService.persist_upload_files`.
3. A MongoDB `bulk_upload_jobs` record is inserted and also held in process memory.
4. A FastAPI background task iterates rows and calls the same `DocumentController.create_document` path for each file.
5. Each successful document may be OCR processed and vectorized.
6. Temp files are intended to be cleaned up by the bulk processing flow.

Bulk job state is partially durable in MongoDB and partially ephemeral in memory.

### Contract Document Save Flow

Contract endpoints live in `backend/rbac_backend/routers/contracts.py`.

Contract upload session:

1. `POST /api/contracts/upload-session`
2. `ContractService.create_upload_session` validates extension (`.pdf`, `.docx`), scope, concurrent session limit, max file size, max chunk size, and TTL.
3. Inserts MongoDB `contract_upload_sessions` with:
   - `upload_id`
   - `filename`
   - `safe_filename`
   - `organization_id`
   - `project_id`
   - `user_id`
   - `status`
   - `max_file_size_bytes`
   - `max_chunk_size_bytes`
   - `max_chunks`
   - `expiresAt`
4. TTL index is created on `expiresAt`.

Multipart contract upload:

1. `POST /api/contracts/upload-multipart`
2. Reads each contract fully into memory.
3. Validates size and MIME against `settings.ALLOWED_CONTRACT_MIMES`.
4. Stores original bytes through contract `_write_to_providers`:
   - Current local path: `contracts/{organization_id}/{project_id or default}/{yyyy}/{mm}/{upload_id}/{upload_id}_{safe_filename}`
   - Current S3 key: same prefix plus stored name
   - Recommended target path: `/ORG/PROJ/contracts/{upload_id}_{safe_filename}`
5. Creates a normal `documents` record with `uploadType="contract"`, `status="queued"`, `contract_upload_id=<upload_id>`, binary paths, tags, file type, size, and `contract_categories=[]`.
6. Marks `contract_upload_sessions.status="queued"`.
7. Writes a separate temp processing copy under `BASE_UPLOAD_PATH/processing/<upload_id>_<safe_filename>`.
8. Enqueues a Redis contract ingestion job.
9. Upserts MongoDB `contract_ingest_jobs` with queued metadata.

Chunked contract upload:

1. `POST /api/contracts/upload-chunk`
2. Chunks are stored in `SECURE_UPLOADS_DIR/__chunks/<org>/<user>/<upload_id>/<chunk>.part`.
3. When the final chunk arrives, chunks are merged into a local final file.
4. Merged bytes are then written again through `_write_to_providers`.
5. A `documents` contract record is created.
6. A separate processing copy is written.
7. Chunk temp folder is removed after scheduling.

### Contract Processing and Versioning Flow

Contract processing queue:

- `ContractIngestQueue` uses Redis lists and hashes.
- Queue names come from settings: `contract_ingest_queue`, `contract_ingest_processing`, `contract_ingest_deadletter`.
- Job hash key: `contract_ingest_job:<upload_id>`.
- Payload includes upload id, document id, org/project, filename, tags, and processing path.
- Retries are controlled by `CONTRACT_QUEUE_MAX_RETRIES`.
- If `CONTRACT_QUEUE_REDIS_URL` is unset, the queue falls back to `settings.FALKORDB_URL`, which means it may use the FalkorDB Redis instance rather than the plain Redis service.

Contract worker flow:

1. Redis worker calls `ContractService.process_ingest_job`.
2. Updates `contract_ingest_jobs.status="processing"`.
3. Updates `documents.status="processing"`.
4. OCR preprocesses the processing copy.
5. `ContractIngestor.ingest_file` extracts text from PDF/DOCX/TXT.
6. Categorizes text through `contract_categorizer`.
7. Optionally runs Marker markdown extraction.
8. Extracts clauses via Marker+LLM spans when available, otherwise regex clause extraction.
9. Builds clause payloads with metadata: `upload_id`, `document_id`, org/project, filename, `uploadType="contract"`, clause number/title/type/level, offsets, page numbers, tags, checksums.
10. Embeds and writes to MongoDB `document_vectors` through `LlamaIndexVectorService`.
11. Writes contract clause vectors to Qdrant through `VectorClient`.
12. Writes contract graph nodes/edges to FalkorDB through `ContractGraphService`.
13. Inserts all clause records into MongoDB `document_vectors`.
14. Updates `contract_ingest_jobs.status="completed"` and `documents.status="completed"` with `contract_categories`.
15. Deletes the temporary processing copy.

Contract versioning:

- No contract binary version record is created.
- Re-uploading the same contract creates a new `documents` record with a new `contract_upload_id`.
- Contract clause chunks include `embedding_version="v1"` and `chunking_version="contract_clause_v1"`, but this is vector schema versioning, not legal document versioning.
- `DocumentGraphPayload.version` is passed as `None`.

### Contract Retrieval Flow

List:

- `GET /api/contracts/list`
- Reads `documents` where `uploadType="contract"` using scope query.
- Returns normalized upload records with document id, upload id, filename, status, categories, error, size, tags, timestamps.

Status:

- `GET /api/contracts/status?upload_id=...`
- Reads MongoDB `contract_ingest_jobs`.
- Does not expose file paths in normalized output.

Download:

- `GET /api/contracts/{document_id}/download`
- Loads a `documents` record where `uploadType="contract"`.
- Prefers local `filepath_local`; falls back to S3 presigned URL from `filepath_s3`.

Search:

- `POST /api/contracts/search`
- Searches MongoDB `document_vectors` where `uploadType="contract"` with lexical regex aggregation.
- Also searches Qdrant via `VectorClient` when enabled.
- Combines lexical and vector candidates with reciprocal rank fusion.
- Rehydrates full clause chunks from MongoDB `document_vectors`.

Contract QA:

- `POST /api/v1/retrieval/contract-qa`
- Requires target contract document status `completed` when `document_id` is specified.
- Uses retrieval service over Qdrant/Mongo `chunks`, not exclusively contract `document_vectors`. This creates a second retrieval path next to `/contracts/search`.

### Other Document-Like Storage

Letters:

- MongoDB `letters` stores generated/drafted letter content, strategy data, sources, graph trace, comments, and `draft_versions`.
- `DraftVersion` is an immutable in-document snapshot for LangGraph draft runs.
- Letter draft versioning is better developed than document/contract binary versioning.
- Letter records do not store uploaded original file binaries.

Letter draft runs:

- MongoDB `letter_draft_runs` stores durable AI drafting run state and artifacts.
- `prompt_templates` stores prompt versions.

Folder hierarchy:

- Inactive router `folder_structure.py` and `FolderService` use MongoDB `folders` for hierarchical folder/file metadata and S3 keys.
- The router is not mounted in `main.py`.
- The implementation has call signature mismatches with `S3Service.upload_file` and settings references like `settings.storage.*` that do not exist in current `Settings`.

Notifications:

- MongoDB `notifications` stores upload events and has enum values for `DOCUMENT_DELETED`, `DOCUMENT_ARCHIVED`, and document version events.
- Current document delete/update/version paths do not emit those events.

Audit logs:

- `utils/audit_logger.py` exists and logs many auth/permission events.
- Document binary lifecycle events are not consistently written as immutable audit events.

## Issues

### Source of Truth and Duplication

1. Original binaries can be written to local and S3, but the system has no canonical provider policy. `storage_locations` records copies, while `filepath_local` and `filepath_s3` also record copies. These fields can drift.
2. Contract uploads write multiple binary copies:
   - Final local/S3 storage copy
   - Merged chunk local file for chunked uploads
   - Separate processing copy
   - OCR processed copy
3. General document processing stores extracted text in `documents.ocrText`, `documents.full_text`, summary `.txt` files, MongoDB `document_vectors.text`, Qdrant payload text, and optionally `chunks.text_original`.
4. Contracts store clause text in MongoDB `document_vectors.text` and Qdrant payloads; they do not write normalized `chunks` unless the separate retrieval ingestion pipeline is run.
5. There are at least three vector write paths:
   - Document OCR pipeline: MongoDB `document_vectors` plus Qdrant through `LangChainVectorService`
   - Contract ingest pipeline: MongoDB `document_vectors` plus Qdrant through `VectorClient`
   - Retrieval ingestion pipeline: MongoDB `chunks` plus Qdrant through `VectorClient`
6. Field naming is inconsistent across vector paths: `organization_id` vs `org_id`, `filepath_local` vs `file_path`, and top-level payload vs nested payload fields.

### Deletion and Retention

1. `DELETE /documents/{id}` deletes only the MongoDB `documents` record.
2. Local files and S3 objects remain orphaned.
3. MongoDB `document_vectors`, `chunks`, `vector_sync_status`, `contract_ingest_jobs`, `contract_upload_sessions`, `document_comments`, notifications, and graph records remain orphaned.
4. Qdrant vectors remain orphaned.
5. FalkorDB graph nodes/edges remain orphaned.
6. There is no trash, archive, legal hold, retention class, purge workflow, or restore flow.
7. Contract upload sessions have TTL, but the document and contract records do not.
8. Redis queue hashes and dead-letter entries have no explicit TTL or retention cleanup.

### Versioning and Immutability

1. General documents have a `version` field but no version table/collection and no immutable file revisions.
2. Contract documents do not support amendment/supplement/version lineage.
3. Metadata updates overwrite current fields without preserving previous values.
4. OCR/AI reprocessing overwrites metadata and vectors without a durable processing run history.
5. Contract graph version is set to `None`.
6. Letter draft versioning exists, but document and contract versioning do not match that maturity.

### Security Risks

1. `S3Service` reads `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, and `S3_REGION`, while settings define `AWS_BUCKET_NAME`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_REGION`. This can silently use bucket `"local-placeholder"` or missing credentials.
2. S3 uploads do not set server-side encryption, object tags, object lock, retention mode, checksum headers, or KMS key IDs.
3. Local files are written as plain bytes without encryption at rest at the application layer.
4. Download endpoints authorize through metadata, but if local paths are tampered with in MongoDB there is no consistent root containment check in the active `/documents/{id}/download` path.
5. Presigned URL lifetime defaults to 60 minutes, but there is no audit event for binary download.
6. File content is read fully into memory for uploads, including contract multipart upload.
7. Contract processing copies and OCR outputs can contain sensitive contract text in temp or uploads directories.
8. In-memory cache keys include Python `hash(query)`, which is process-randomized and not stable across restarts. Cached AI search results may contain sensitive snippets in process memory.
9. Redis queue falls back to `FALKORDB_URL`, risking queue data and graph data sharing the same Redis/Falkor instance.

### Performance and Scalability

1. Large upload files are read fully into memory in document and contract endpoints.
2. Qdrant and Mongo vector dual writes happen in request-adjacent/background flows without a single durable vector outbox.
3. General background jobs are in-process only; a process restart loses pending document OCR jobs.
4. Bulk job state is split between MongoDB and process memory.
5. Contract queue is Redis-backed, but processing path depends on a local temp file. If the worker runs on a different host/container without shared storage, the job fails.
6. Contract lexical search uses regex over `document_vectors.text`; this is expensive at scale despite a text index and can produce poor ranking.
7. MongoDB `document_vectors` stores full embedding arrays and text chunks; this can become expensive and large if Qdrant is the primary vector index.
8. No object checksum or dedupe is enforced for original binaries, so duplicate uploads multiply file, vector, and graph storage.
9. Contract chunked upload detects completion by `chunkIndex == totalChunks - 1`, not by verifying all chunks have arrived first. Out-of-order upload can trigger premature merge and fail.

### Data Model and Consistency

1. Contract documents are first-class enough to have a separate router and ingest pipeline, but not first-class enough to have a contract-specific aggregate/root collection.
2. Contract status exists in both `documents.status` and `contract_ingest_jobs.status`; they can diverge.
3. Contract categories exist in both `documents.contract_categories` and `contract_ingest_jobs.categories`.
4. `document_vectors` mixes normal correspondence chunks and contract clause chunks with different schemas.
5. `DocumentVector` model only allows `uploadType` `incoming|outgoing`, but contract chunks are stored with `uploadType="contract"`.
6. `DatabaseService._find_existing_document` falls back to matching by filename, which can update the wrong document when duplicate filenames exist.
7. `DocumentService.create_document` creates a supplied ObjectId, then removes `_id` before insert, causing MongoDB to generate another id in the keyword construction path. Contract path supplies a `Document` model and does not follow the same generated id behavior.
8. Active enclosure flow does not store enclosure bytes.
9. Inactive/legacy document and folder routers duplicate storage logic and increase maintenance risk.

### Observability and Audit

1. There is vector sync bookkeeping, but no unified storage reconciliation status for binary objects, Mongo metadata, vectors, graph, and Redis queue.
2. `storage_sync` can detect missing local files, but delete/update flows do not use it transactionally.
3. No immutable audit trail captures document create/update/delete/download/reprocess/vectorize/archive events.
4. Notifications define archival/version/deletion events, but current document lifecycle does not emit them.

### Cost Inefficiency

1. Embeddings are stored both in MongoDB `document_vectors` and Qdrant.
2. Text chunks are duplicated in multiple collections and vector payloads.
3. Contract upload copies inflate storage cost.
4. No lifecycle transition to cheaper object storage classes exists.
5. No dedupe by SHA-256 for identical files or identical extracted chunks.

## Recommendations

### Canonical Storage Path Policy

Use one relative storage-key policy for every provider. Local storage should prepend `SECURE_UPLOADS_DIR`; S3 should use the same relative key as the object key. Do not let local and S3 build different folder structures.

Recommended paths:

| Document class | Canonical relative path |
| --- | --- |
| Incoming correspondence | `/ORG/PROJ/incoming/{yyyy}/{mm}/{upload_id}_{safe_letter_no}{ext}` |
| Outgoing correspondence | `/ORG/PROJ/outgoing/{yyyy}/{mm}/{upload_id}_{safe_letter_no}{ext}` |
| Contract document | `/ORG/PROJ/contracts/{upload_id}_{safe_filename}` |
| Enclosures | `/ORG/PROJ/enclosures/{yyyy}/{mm}/{parent_document_id}/{upload_id}_{safe_filename}` |
| Derived processing artifacts | `/ORG/PROJ/derived/{document_id}/{version_id}/{artifact_type}` |

Policy details:

- `ORG` and `PROJ` should be stable short names from `storage_settings`, not mutable display names. If short names are missing, use stable ids.
- `upload_id` must be generated before writing bytes and reused in the filename, Mongo metadata, queue payload, and audit event.
- For incoming/outgoing documents, the stored file name must use sanitized `letterNo` plus the original extension: `{upload_id}_{safe_letter_no}{ext}`.
- For contracts and enclosures, `safe_filename` can continue to be a sanitized original filename unless a contract-number/enclosure-number policy is introduced.
- The chosen stored filename must be sanitized once and reused unchanged across providers.
- Incoming/outgoing correspondence should include `{yyyy}/{mm}` because volume grows continuously and users often browse by communication period.
- Contracts should not include `{yyyy}/{mm}` by default because the contract folder should act as the project-level contract master area. If contract packages become large, add a package segment later: `/ORG/PROJ/contracts/{package_code}/{upload_id}_{safe_filename}`.
- Store the final relative key in a single field such as `storage_key`; keep provider-specific records in `storage_locations`.
- Deprecate direct business logic reads from `filepath_local` and `filepath_s3`; derive those from `file_objects` or provider config.

Required code changes:

- Change `DocumentController._write_to_providers` to generate `upload_id` and `safe_letter_no` before calling `SecureFileService.store_document`.
- Add `{yyyy}`, `{mm}`, `{upload_id}`, `{safe_letter_no}`, and `{ext}` substitution support to `StorageSettingsService._normalize_paths`, or introduce a dedicated `StorageKeyBuilder`.
- For `/api/documents`, use:
  - incoming: `/ORG/PROJ/incoming/{yyyy}/{mm}/{upload_id}_{safe_letter_no}{ext}`
  - outgoing: `/ORG/PROJ/outgoing/{yyyy}/{mm}/{upload_id}_{safe_letter_no}{ext}`
- For `/api/contracts/*`, replace `_storage_path_prefix` and `_stored_filename` behavior with `/ORG/PROJ/contracts/{upload_id}_{safe_filename}`.
- Persist the generated key on the document record and use the same key for S3 object storage.
- Add tests for incoming, outgoing, contract multipart, and contract chunked uploads to assert exact paths.

### General Documents

1. Introduce a canonical `document_files` or `file_objects` collection.
   - Store immutable file object records: `file_object_id`, `sha256`, `size`, `mime`, `original_filename`, `storage_provider`, `bucket`, `key`, `encryption`, `created_by`, `created_at`, `retention_policy`, `legal_hold`.
   - Let `documents.current_file_object_id` point to the active binary.
   - Move `filepath_local` and `filepath_s3` out of the primary document record over time.

2. Add `document_versions`.
   - Every binary replacement or metadata reprocessing creates a version record.
   - Store `version_number`, `file_object_id`, `metadata_snapshot`, `ocr_text_ref`, `vector_generation_id`, `status`, `created_by`, `created_at`, and `reason`.
   - Make old versions immutable.

3. Replace hard delete with lifecycle states.
   - `active`, `archived`, `trash`, `purge_pending`, `purged`, `legal_hold`.
   - Only purge after retention and authorization checks.
   - Purge should remove or tombstone Mongo records, object storage, local files, Qdrant points, Mongo chunks, and graph nodes in one orchestrated workflow.

4. Fix enclosure storage immediately.
   - Store enclosure bytes through the same file object service.
   - Put enclosure metadata in `document_enclosures` or `documents.enclosures` referencing `file_object_id`.

5. Standardize vector indexing.
   - Choose one canonical chunk collection (`chunks`) and one canonical vector index (`Qdrant`) for retrieval.
   - Keep MongoDB `document_vectors` only if it is intentionally the lexical/searchable evidence store, otherwise migrate to `chunks`.
   - Use a single metadata schema with `org_id`, `project_id`, `document_id`, `version_id`, `chunk_id`, `document_type`, `source`.

6. Implement durable processing jobs.
   - Use Redis/RQ/Celery/Arq or Mongo outbox for all document OCR/vector jobs, not only contracts.
   - Store job payloads by stable object keys, not local temp paths.

7. Add binary checksum and dedupe.
   - Compute SHA-256 at upload stream time.
   - Reject exact duplicates per project or link new documents to an existing immutable file object.

8. Harden downloads.
   - Validate local paths are inside the configured storage root.
   - Emit audit events for every binary download and presigned URL generation.
   - Prefer object storage presigned downloads in production.

9. Fix S3 configuration.
   - Make `S3Service` read `AWS_BUCKET_NAME`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_REGION`, or rename settings consistently.
   - Add SSE-S3/SSE-KMS, checksum, content disposition, object tags, lifecycle class, and object lock settings.

10. Add storage reconciliation and repair.
    - A scheduled job should compare `documents`, file objects, local/S3 existence, Mongo chunks, Qdrant points, graph nodes, and job state.
    - Persist reconciliation runs in `storage_reconciliation_runs`.

### Contract Documents

1. Create a `contracts` aggregate collection.
   - Fields: `contract_id`, `organization_id`, `project_id`, `title`, `contract_number`, `package`, `status`, `current_version_id`, `created_by`, `created_at`, `access_policy_id`.
   - A contract can have multiple immutable versions.

2. Create `contract_versions`.
   - Fields: `contract_version_id`, `contract_id`, `version_number`, `file_object_id`, `sha256`, `effective_date`, `uploaded_by`, `uploaded_at`, `supersedes_version_id`, `change_reason`, `legal_hold`, `retention_policy`, `ingestion_status`.
   - Never overwrite version contents.

3. Link clause chunks to contract versions.
   - Clause metadata must include `contract_id`, `contract_version_id`, `clause_id`, `clause_number`, `clause_title`, `page_numbers`, `chunk_index`, `chunking_version`, `embedding_version`.
   - Search should default to the current version but allow explicit version selection and comparison.

4. Make contract ingestion idempotent.
   - Job key should be `contract_version_id`.
   - Reprocessing should replace only chunks/vectors for that version.
   - Do not rely on local `processing_path`; workers should materialize from object storage by `file_object_id`.

5. Add contract immutability controls.
   - Use S3 Object Lock or equivalent for executed contract versions.
   - Add KMS encryption and per-tenant/project key strategy where possible.
   - Store checksums and verify before processing and before download.

6. Add contract audit trail.
   - Events: session created, upload completed, checksum calculated, ingestion queued, OCR completed, clauses extracted, vectors indexed, graph synced, download, version archived, version superseded, legal hold changed, purge requested, purge completed.
   - Store in `document_audit_events` or `contract_audit_events`.

7. Split contract status from document correspondence status.
   - Avoid using `documents.status` for both workflow status and contract ingest status.
   - Use `contract_versions.ingestion_status` and `contracts.lifecycle_status`.

8. Reduce contract duplicate storage.
   - Keep one immutable original object.
   - Use short-lived temp files only during processing and guarantee cleanup.
   - Store OCR output and Marker markdown as derived artifacts linked to version id, preferably in object storage if large.

9. Improve contract search architecture.
   - Use Qdrant for vector retrieval and Mongo/OpenSearch for lexical search.
   - Avoid regex scanning of large `document_vectors.text` at scale.
   - Maintain a clause evidence collection optimized for filtering and display.

10. Add retention policies.
    - Contract originals: long-term immutable retention, legal hold capable.
    - Derived OCR/markdown: retain while contract version exists, or regenerate if cheaper.
    - Vectors: regenerable, can be purged/rebuilt.
    - Queue and processing logs: shorter retention with error samples preserved.

## Proposed Architecture

### Storage Architecture Map

Proposed logical ownership:

```text
Client
  -> API upload endpoint
    -> Upload/session validator
      -> FileObjectService
        -> stream bytes to object storage/local provider
        -> compute sha256 and size
        -> write file_objects metadata
      -> Domain record
        -> documents for correspondence
        -> contracts + contract_versions for contracts
      -> Durable job queue
        -> processing_jobs / Redis queue

Worker
  -> materialize file by file_object_id
  -> OCR / parse / metadata extraction
  -> store derived artifacts
  -> chunk text
  -> write chunks/evidence collection
  -> upsert Qdrant vectors
  -> upsert FalkorDB graph
  -> update processing status
  -> write audit events

Read paths
  -> Metadata/list: MongoDB domain collections
  -> Binary download: file_objects -> provider presigned URL or safe local stream
  -> Search/RAG: Qdrant + chunks/evidence + MongoDB metadata
  -> Contract graph: FalkorDB graph scoped by org/project/contract_version

Delete/archive paths
  -> lifecycle state change first
  -> retention/legal-hold check
  -> async purge job
  -> delete/tombstone provider object, chunks, vectors, graph, queue state
  -> immutable audit event
```

### Proposed Collections

| Collection | Purpose |
| --- | --- |
| `documents` | Correspondence/document business record, current metadata, lifecycle state |
| `document_versions` | Immutable document metadata/file version snapshots |
| `contracts` | Contract aggregate/root record |
| `contract_versions` | Immutable contract binary/version records |
| `file_objects` | Canonical binary/object metadata for originals and enclosures |
| `derived_artifacts` | OCR text, Marker markdown, summaries, extracted JSON, processing outputs |
| `chunks` | Canonical text/evidence chunks for all document types |
| `vector_sync_status` | Sync state for Qdrant per document/version |
| `processing_jobs` | Durable OCR/vector/contract ingest job state |
| `document_audit_events` | Immutable lifecycle/download/update audit trail |
| `storage_reconciliation_runs` | Scheduled integrity checks and repair status |

### Proposed Document Save Flow

1. API validates auth, scope, MIME, and size while streaming upload.
2. API generates `upload_id`, extracts the original file extension, and derives `safe_letter_no` from `letterNo`.
3. `StorageKeyBuilder` creates the canonical key:
   - incoming: `/ORG/PROJ/incoming/{yyyy}/{mm}/{upload_id}_{safe_letter_no}{ext}`
   - outgoing: `/ORG/PROJ/outgoing/{yyyy}/{mm}/{upload_id}_{safe_letter_no}{ext}`
4. `FileObjectService` writes original bytes to configured storage provider using that key.
5. It computes SHA-256, captures provider details, and inserts `file_objects`.
6. API creates `documents` plus `document_versions` version 1.
7. API enqueues a durable processing job referencing `document_version_id`.
8. Worker processes from file object, writes derived artifacts, chunks, vectors, graph, and audit events.

### Proposed Contract Save Flow

1. API creates upload session and reserves `contract_id` or receives target contract.
2. API generates or reuses `upload_id` and sanitizes the filename.
3. `StorageKeyBuilder` creates `/ORG/PROJ/contracts/{upload_id}_{safe_filename}`.
4. Upload completion creates immutable `file_objects` record at that key.
5. API creates `contract_versions` version N and updates `contracts.current_version_id` only after validation.
6. Queue job references `contract_version_id`, not a temp file path.
7. Worker processes exact immutable version and writes clause chunks/vectors/graph with version ids.
8. Search and QA filter by `contract_id` and `contract_version_id`.

### Proposed Deletion and Retention Flow

1. User delete request sets lifecycle state to `trash` or `archive`.
2. Audit event is written immediately.
3. Retention engine checks legal hold and policy.
4. Purge job deletes provider objects, derived artifacts, chunks, Qdrant points, and graph nodes.
5. Domain records are tombstoned, not physically removed, unless policy allows full purge.
6. Reconciliation verifies no orphaned storage remains.
